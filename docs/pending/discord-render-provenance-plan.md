# Held plan: prove non-AI render contributors

The channel-read prototype withholds newly scoped restricted card information when AI artwork is disabled. The current asset origin on a subject, or a render's `source_hash` matching its edition, is not proof of all contributors to the published bytes. The provisioning script hashes a card manifest object; the renderer also fetches a background and may fetch a collection logo separately. The render upload accepts output bytes and copies the edition hash into the render record. These records do not by themselves establish which bytes were actually combined.

## Inventory without disclosure

Before any backfill, use a read-only, access-controlled aggregate and private evidence directory. Count candidate variants, missing/unknown source or background origins, missing/invalid dependency records, published render/hash mismatches, and independent collection-logo references. Keep private IDs, rosters, manifests and images out of commits and PRs. Bound each extraction by a stable cursor and a small page size; fail rather than silently treating missing pages, invalid JSON, duplicate keys, missing assets, cross-tenant references or ambiguous graph edges as safe. The initial operator-side audit is **not** an authorisation grant.

## Proof path

1. Freeze the exact card, edition, variant, published render, Bot collection policy, artwork preference, asset metadata and relevant collection-logo revision in a private manifest. Include source-asset byte hashes, every derivative/dependency edge, background and logo bytes, composition, material/effect inputs, font and renderer dependencies, source revision and toolchain versions. The record must prove completeness, not simply list currently referenced assets. A current reference or an edition source hash is insufficient to establish historic inputs.
2. Starting from the actual published render, verify each contributor transitively with a bounded traversal and explicit limits for depth, node count and input bytes. Cycles, missing nodes, unrecognised origin, AI-assisted/generated sources, oversized/malformed dependency data and unknown recipe or logo inputs fail closed. Do not treat a self-declared receipt as verification.
3. Where all historical inputs and the exact renderer are recoverable, reproduce the output in a network-disabled environment and compare its bytes and hash to the published render. If exact reproduction or contributor completeness cannot be independently verified, retain `unknown`; never infer non-AI status from appearance, an empty dependency array, or a matching edition hash. For unrecoverable renders, a separately approved new render with recorded inputs can produce a new immutable revision; it must not overwrite the old evidence or claim the old render was proven.
4. Propose a separately reviewed, versioned proof record keyed to the **specific render and immutable input hashes**, not an editable card-wide boolean. Validation must recheck its input versions and live Bot policy at the same guarded read used for delivery. Revocation, source replacement, collection/logo change, renderer changes or mismatch invalidate the proof. The schema, trust boundary, rollback compatibility and invalidation triggers are not designed or applied by this draft.
5. Test synthetic direct and transitive AI inputs, an unrecorded logo, a missing/cross-tenant asset, malformed/oversized dependencies, cycles, stale render/recipe/composition/mark hashes, input mutation during validation, conflicting proofs, bounded-work and crash/retry. Unknown or incomplete evidence must never produce a safe result. Test current-authority revocation before the guarded read and separately document the unavoidable interval between that read and Discord's external delivery.

## Controlled production operation

Only after independent review and an approved schema/rollback plan: inspect current live state and policy, take the required D1 JSON backup, save private evidence, run a bounded dry run, verify an immutable snapshot and proposed writes, then perform an idempotent, reversible operation in small batches. Record failures and stop on changed inputs or count mismatches. Preserve all original renders, cards, inventory and ledger history. Re-check live policy before every read and run a separately authorised live smoke. No production change, render batch or policy widening is authorised by this document.

For a collection whose historical inputs cannot be proven, the proposed recovery path is a **new** render revision, not a backfill that asserts an unknown old render's history:

1. Select one explicitly approved collection and at most ten variants for an initial private dry run. Capture the exact enabled/publication state, old render IDs, R2 object hashes and all live references in a private manifest. Download the old outputs into a protected backup, hash them against D1 and independently verify the backup can be read; a D1 JSON backup alone does not preserve R2 bytes.
2. Resolve all subject, background, collection mark, recipe, material, effect, composition and font inputs by immutable ID and SHA-256. Set a per-input and aggregate byte ceiling before reading; reject unavailable or changed bytes and all unknown/AI/transitively ambiguous contributors. Include the exact renderer source tree, lockfile, runtime, Sharp/libvips and font versions. If the historic logo or toolchain is missing, classify the old output as unproven instead of guessing.
3. Render each candidate twice in an isolated network-disabled environment, with no paid generation or production access. Require exact output-byte equality between the two runs, record the input manifest and output hash, and independently verify the manifest and hashes. A match with an old output can establish that those bytes are reproducible from the recorded inputs; it does not prove the historical production process. Any nondeterminism or mismatch remains unqualified.
4. Before an approved cutover, implement a trusted, reviewed publisher that uploads new content-addressed objects without replacing old ones, verifies R2 read-back hashes, and atomically checks the same Bot/collection/render/input revisions before inserting the proof and switching each render pointer. Abort a batch on any changed state; do not reuse the current generic render upload as provenance proof. Limit later batches and provider/storage costs to separately approved ceilings.
5. Retain the old object and pointer snapshot. Rollback must compare the current pointer and revision to the newly published value before restoring the prior pointer; if anything changed since cutover, stop for review rather than overwriting it. Verify the restored bytes and authority, and do not delete either R2 version as part of rollback. Test interrupted upload, proof/pointer failure, concurrent edits, partial batch and rollback races on disposable D1/R2 first.

The current candidate does not implement that publisher, a verifiable contributor graph, proof invalidation, or this cutover. Those are prerequisites, not instructions to start a production render job.

The experimental channel-read tests demonstrate the fail-closed response for AI-off restricted collections, including a sourced subject with a matching edition hash. They do not qualify a complete lineage verifier or unblock the live channel.

## Cutover contract to implement and review

This is a design contract, not an executable production procedure. The synthetic publisher uses local SQLite and local files; it cannot establish production provenance or modify D1 or R2. A production implementation must first supply the following reviewed capabilities:

- Create a D1 JSON backup with `node scripts/backup-d1-json.mjs`; separately copy every affected old R2 object to protected backup storage, verify each copy's bytes against the captured SHA-256, and rehearse read-back before any cutover. Retain the prior render IDs, object keys, hashes, policy, and monotonically increasing pointer revisions in private evidence.
- Select at most ten variants from one approved collection, with explicit input/output byte and cost ceilings. Freeze the actual, complete contributor graph, renderer and native runtime; independently verify them. A sandboxed double render and a self-signed receipt alone do not establish provenance. Stop on unknown lineage, changed state, missing backups, or unequal output bytes.
- Upload each new object under its content-addressed key without replacing an existing object, then independently read it back and hash its bytes. Upload precedes the database transaction; an interrupted or rejected transaction may leave unreferenced objects, which remain preserved for later reviewed cleanup.
- In one D1 transaction, recheck all authorization, Bot and collection policy, input/recipe/mark hashes, lifecycle and old pointer/revision snapshots; insert render-specific proof and audit records and conditionally advance every target pointer. Any mismatch aborts the whole batch. A monotonic revision prevents an intervening change-and-revert from masquerading as the captured state. The schema, its invalidation guarantees, and compatibility with rollback Workers still require design and testing.
- Roll back only after verifying the preserved old object bytes. Restore pointers in one guarded transaction only when every current pointer and revision still matches that cutover; increment revisions again and record the rollback. If any pointer changed, stop rather than overwrite a later edit. Retain both object versions and verify the restored read path. No database backup automatically reverses a schema migration.

The disposable local prototype has a ten-variant limit, 5 MB per input, 50 MB total inputs, 10 MB per output and 50 MB total outputs. These are test bounds, not approved production limits. Its local atomic object promotion and SQLite revision checks illustrate the contract but do not prove equivalent R2/D1 behavior, a fully trusted toolchain, safe production lineage, or isolation from an external deployment.

The synthetic experiment's contributor graph and input labels are caller-declared, and its `node_modules` and renderer runtime binaries are not captured immutably. Double-render equality therefore does not establish trusted provenance. A trusted source manifest and an independently pinned, immutable complete toolchain are prerequisites before any D1/R2 implementation or production proposal.

The subsequent local signed-manifest experiment verifies an independently supplied Ed25519 key, a specific operation and toolchain bundle hash, canonical bytes, expiry, input hashes and bounds before copying fixture bytes into a new private sandbox. It does not verify that the signer inspected all contributors, that the toolchain bundle contains its claimed complete executable closure, or that a renderer executes only those copied bytes. The capture directory is owner-writable, not an immutable mount; race-free execution, offline isolation, trusted key governance and artifact attestation remain open. Do not use this fixture verifier as production authorisation.
