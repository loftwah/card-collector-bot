# Held Discord global binding experiment

The SQL alongside this note is an **unnumbered local experiment**, not an approved migration. It retains a global Discord-ID-to-Foilbury-user binding across tenant links and Worker rollback. It fails if historical rows bind one Discord ID to multiple users, including revoked rows; no winner is inferred and no account is merged. A persistent registry survives deletion of all tenant-specific links. Revocation does not grant another account the Discord ID.

A first binding needs a one-use admission row, created and consumed in the *same atomic D1 batch* as the verified account, membership and identity writes. The held Worker candidate now creates and checks consumption of that row for first interaction and OAuth linking. Old Workers can continue using a pre-existing same-account binding, but new onboarding is deliberately unavailable after rollback. Additional experimental reserved-email triggers stop the old first-interaction path's separate user, membership and wallet inserts in local tests. Those triggers can also deny operations on pre-existing reserved-email orphans and require compatibility review.

The old OAuth helper can create a zero-balance wallet for an existing ordinary account before its unpermitted link is rejected. That wallet is indistinguishable at the database boundary from one created by normal product flows. A deterministic local test records this partial side effect. This proposal does not establish a no-partial-write rollback.

The proposed rollback target is a separately built, pinned compatibility Worker based on the prior production version. It must respond with a temporary-unavailable result before executing application logic for both implementations of `/api/discord/interactions` (`src/worker.ts` and the Astro API route) and for `/auth/discord/start` and `/auth/discord/callback`. It retains the additive schema and all accounts, inventory, balances and identities; normal non-Discord routes continue. Prebuild and independently test that exact Worker and its artifact before the schema change; verify the actual deployed version after rollback. The existing legacy Worker is not an allowed rollback target after installing this schema. A dedicated prototype entrypoint now blocks Discord API/auth paths and delegates other traffic; a disposable build served a synthetic local homepage and blocked the tested Discord paths. It was built from the draft, not the exact prior production version, and has not been deployed or qualified as the rollback artifact. Infrastructure-level routing or another deployer could bypass this procedure, so deployment control and propagation must also be reviewed.

Never commit admission permits on their own. A committed unused permit is an authorization capability and could let a later old Worker claim the matching account; a local test of batch rollback is not proof that every production writer obeys this rule. Review all writer paths, session issuance, failure and crash cases before activation. The SQL protections assume trusted migration and D1 administration; an actor with arbitrary DDL or direct registry access can bypass them. SQLite `INSERT OR REPLACE` against the registry is not an approved operation. Retention and deletion obligations need an explicit policy before production.

## Conflict and recovery

Inventory existing bindings privately and quantify conflicting IDs before migration. Hold each conflict for verified identity and ownership review, including account history, inventory and ledger; there is no automated choice or email-based merge. The migration preflight aborts on any conflict, and must run in the same atomic batch as registry backfill and trigger installation, so an old writer cannot slip between the audit and enforcement. Validate that the chosen production migration runner actually offers this all-or-nothing behavior; do not infer it from the SQL file alone. Back up D1 and prepare a tested rollback before any approved production change.

Cloudflare documents [`D1Database.batch()`](https://developers.cloudflare.com/d1/worker-api/d1-database/) as a transactional sequence that rolls back on failure. A disposable `wrangler d1 migrations apply --local` fixture rolled back an earlier table creation when a later statement failed. The existing production technical release script only checks migration names and does not apply migrations; the actual approved production migration runner and its remote behavior remain to be established.

An email-only orphan has no proven Discord binding, even if its address and password sentinel look Discord-generated. An explicit recovery flow must authenticate the existing Foilbury account with recent strong authentication, complete Discord OAuth, and obtain deliberate confirmation of the account being linked. Its short-lived, single-use challenge must bind the Foilbury session, user, Bot and verified Discord ID; the transaction must recheck the unrevoked session, strong-auth time, active account/membership and registry before consuming the challenge and creating the permit and binding. Do not revive revoked identity rows or merge based on email. If the person cannot authenticate the account, a separate audited human verification and recovery procedure is required; simply proving control of Discord or matching an email is insufficient.

A default-off prototype now connects an explicit CSRF-protected form to a session-bound OAuth state and PKCE exchange, a confirmation form, transactional audit, current-authority receipt replay, per-user quota and scheduled bounded cleanup. It is enabled only by `FOILBURY_DISCORD_RECOVERY_ENABLED=1`; never enable it without the reviewed pending schemas and a qualified rollout. While disabled, signed-in generic OAuth callbacks retain the existing implicit account-link path, including its lack of explicit strong-auth confirmation. When enabled, those callbacks redirect to the deliberate recovery flow instead; that compatibility change requires review. The Worker candidate itself still depends on the unnumbered binding schema even with recovery disabled, so this switch is not a safe pre-migration deployment strategy. Provider exchanges in automated route tests are stubbed; a disposable local Worker exercised the confirmation screen using a synthetic challenge, not an actual Discord OAuth journey. Independent security review, real provider interaction, rendered acceptance and operational recovery remain open.

## Size and deployment limits

The proposal adds a covering index and one persistent registry row per distinct Discord ID. A preflight examines at most 10,001 rows and aborts before schema creation above the experimental 10,000-row cap. Below the cap the backfill and conflict scan read all identity rows; index construction and table insertion consume database storage and write/CPU budget. This row cap does not bound byte size, remote latency or resource use. SQLite tests measure only a synthetic in-memory 10,000-row fixture and do not predict remote D1 latency, row charges, lock time or available capacity. Measure representative production cardinality and staging performance, check D1 limits, and establish a maintenance/capacity plan before attempting it. The admission table should be empty after successful batches; monitor and investigate any committed permit rather than automatically consuming or deleting it.

Do not apply this schema in production or claim that this experiment completes Discord delivery, transaction-time policy fencing, live mobile acceptance, or the demo.
