# API dispatch follow-up

This is a bounded follow-up to issue #16, based on `d4d35f1` and then rebased as needed. The earlier gift/receipt and trade/detail shadowing fixes were already present: list routes match one segment and the receipt/detail routes have their own exact patterns. The peer directory and administrative member list also have separate handlers. This follow-up does not by itself close the issue's full route, role or UI acceptance criteria.

The previous dispatcher still had 68 method branches whose conditions accepted extra segments. Examples included `GET me/preferences/extra`, `POST rewards/claim/extra`, `POST draws/extra`, `POST trades/{id}/accept/extra` and administrative mutation routes. They now require their declared segment count. A single trailing slash remains accepted; empty interior segments and repeated trailing slashes are rejected. `tests/fixtures/api-suffix-regressions.json` records each affected method and a concrete extra-suffix request. `tests/workers/api-dispatch-http.test.ts` sends all of them through the Astro API handler, verifies 404, and checks representative reward and preference state is unchanged. The syntax check in `tests/scripts/api-dispatch-shape.test.mjs` is a guard against one class of future regression, not a proof that all route precedence or permissions are correct.

The same HTTP test exercises gift list versus received award, trade list versus detail, normal player versus administrative member list, and agent directory scopes. Ordinary peer discovery now excludes revoked memberships and synthetic users that cannot participate in human trades. OpenAPI now distinguishes those resources, accepts the existing `recipientId` or explicit-email trade input, and uses the canonical local origin. The browser `TradeDesk` uses IDs for member discovery and trade details; the gifts page calls the shared receipt reader. The CLI and MCP trade creation retain explicit-email compatibility. `StudioWallet` now uses the actual `id` returned by the administrative member endpoint; its intercepted component test confirms the chosen ID appears in the grant URL.

Still open: the administrative member list exposes email to `ensureOps` callers, including content/economy/grants capabilities, and its intended contact-access policy needs a deliberate least-privilege contract and consumer migration. The separate peer-shelf containment does not establish consent to expose visible-card ownership. Historical trade-detail privacy after audience changes, complete artwork-lineage policy, other direct Astro API routes, and a complete method/role/schema/side-effect inventory remain unqualified. The mocked Studio test is not a real grant or a native-device accessibility review. No production data was mutated and no deployment is implied.
